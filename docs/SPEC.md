# PiMate — プロダクト方針

**更新日:** 2026-10-13  
**状態:** 開発方針。技術的成立性はPoCで検証する。  
**対象:** iOS / Androidアプリ、macOS / Linux上のPi

> この文書は「何を実現するか」「今回合意した技術方針」「変えてはいけない前提」を記録するものです。実装仕様書ではありません。詳細設計・技術選定・実装手順・テスト設計はCodexやClaude Codeなどのコーディングエージェントに委ねます。

## 1. 目指す体験

PiMateは、**PC上で実行する通常のPi Coding Agentを、スマホに最適化したネイティブUIから使えるアプリ**です。ターミナルの縮小表示や遠隔操作アプリではありません。

実現したい体験は次のとおりです。

- **PC → スマホ:** PCで通常どおり `pi` を起動して作業し、その**同じ実行中のPi**をスマホから確認・操作できる。
- **スマホ → PC:** スマホから独立したPiを新規起動し、あとからPCのターミナルで**同じ実行中のPi TUI**に接続して作業を引き継げる。
- **複数Pi:** プロジェクトやPiインスタンスを切り替え、複数の作業を並行して管理できる。
- **スマホで完結:** Pi標準CLIの主要機能を、スマホ向けUIから扱える。会話、モデル・Thinking設定、履歴、ツール実行、Diff、作業状況やサブエージェントの確認を重視する。
- **切断に強い:** スマホのアプリ切替、回線断、再接続でPiの実行が不必要に停止せず、現在の状態へ安全に復帰できる。

### UIの方向性

参考は [ompanion](https://github.com/edde746/ompanion)、T3 Codeのモバイルアプリ、ChatGPTアプリです。個々の画面構成やコンポーネントは実装時に設計します。

- **ライトテーマ中心**で、ミニマルかつ落ち着いた見た目にする。ダークテーマも用意する。
- **配色:** ニュートラルグレーのモノクロ基調に、**緑系のアクセント1色**。それ以外の色は状態（作業中・入力待ち・エラー）やDiffなど、意味のある箇所に限る。アクセントと、Diffの追加行・成功表示の緑が混同されないよう配慮する。
- **区切り:** 線や影に頼らず、面の濃淡と余白で区切る。
- **情報密度:** ompanion程度の高密度を基準とする。完了したターンの作業は要約行に畳み、ツール呼び出しは簡潔な行で示して必要なときに展開する。
- **ナビゲーション:** ChatGPTアプリ型の左ドロワーでPi Instanceを切り替え、メイン画面はチャットとする。
- **一覧の単位は、会話ではなく実行中のPi Instance。** 各Instanceの現在のセッション、状態、起動元（PC / スマホ）を示し、入力待ちのInstanceを目立たせる。
- **エージェント側からの確認・選択・入力要求はチャット内に表示**し、モーダルで作業を塞がない。モデル選択など、ユーザー自身が開く操作はモバイルの標準的な作法に従う。
- Piは標準ではツール実行ごとの承認を求めないため、承認操作を前提とした画面構成にしない。

## 2. 合意済みの技術方針

### 通常Piとの互換性

- **Pi本体のフォークや改造は前提としない。** ユーザーはPCで普段どおり `pi` コマンドを使える。
- **Piの通常TUIを実行する。** メインの実行・制御経路としてPi RPCモードやPi SDKで作り直したエージェントを採用しない。
- **共通のRemote Control Extensionを使用する。** PCから通常起動したPiも、スマホから新規作成したPiも、このExtensionを通じて同じ方式でイベント取得・操作を行う。
- **Pi自身が会話履歴・設定・認証・Extension・Skillsの正本。** PiMate側に別のエージェント実装や独立した会話状態を作って互換性を損なわない。

### スマホからの新規Pi起動

- **abducoを第一候補とする。** スマホから作るPiはPC上の独立プロセスとして通常TUIを起動し、abducoのPTYセッションで保持する。
- PCから必要なときにAttach / Detachでき、Piを終了させずスマホ操作を継続できることを目指す。
- **abducoの実行ファイルをExtensionパッケージに同梱**し、macOS / Linuxの利用者に手動導入を極力要求しない。
- tmuxを必須にはしない。**abducoは採用候補であって、PoCでの成立確認前に完成済みの前提にしない。**
- 既にPC上で普通に起動されていたPiを、あとからabduco配下へ移す機能は要求しない。

### 配布・Host・通信

- ユーザー向けの導入は、**Pi Extensionパッケージ1つのインストール → 初回セットアップ → スマホとのペアリング**を目指す。
- 同一パッケージに軽量な**Host Service**を含める。HostはPiの発見、接続・認証、スマホ発Piの起動と管理を担当する。
- HostはPiとは**独立したプロセス**とし、Piをすべて閉じた状態でも、設定済みのHostからスマホ発Piを新規作成できる。
- 通信方法、内部IPC、常駐方式、バイナリ配布・更新方法の詳細は実装側で判断する。
- インターネット越しの接続にも拡張できる構成を目指す。Relayの運用形態は未決定。

### セッションとExtension

- **Piインスタンス（実行中プロセス）とPiの会話セッションを区別する。** Pi TUIで `/new` や `/resume` を実行しても、スマホは同じPiインスタンスに追従して現在の会話へ同期する。
- 第三者Extensionは、まず**PCの通常Pi環境でそのまま実行できること**を重視する。ツール実行の互換性とUIの互換性は別に評価する。
- 標準的な確認・選択・入力UIはスマホでも操作できるよう目指す。独自の `ctx.ui.custom()` など、任意の拡張TUIの自動変換は保証しない。
- 未対応の操作や入力待ちは明示し、黙って無視・承認しない。

## 3. 非目標と守るべき制約

- Piをスマホ端末内で実行することは目指さない。実行場所はユーザーのPC / サーバー。
- スマホでターミナルをミラー表示する方式を主UIにしない。
- リモート操作を実現するために、TTYへの疑似キー入力をPiの主要制御経路として使わない。
- 接続断・セッション切替・複数端末操作で、別のPiや会話に誤送信しない。操作の重複、自動再送、勝手な承認を避ける。
- リモートから任意のOSコマンドを無制限に実行できる管理APIを公開しない。端末認証・権限・作業領域・秘密情報を安全に扱う。
- 初回セットアップでの常駐登録や外部公開など、影響のある操作はユーザーの同意なしに実行しない。

## 4. コーディングエージェントに任せること

上記の体験と方針を満たす限り、次は**実装担当の裁量**とします。

- アプリ内部のアーキテクチャ、画面設計、状態管理、使用ライブラリ
- Extension / Host間の通信プロトコル、プロセス識別、同期・復旧方式
- abducoのセッション運用、OS別バイナリの配布・更新、PCからのAttach UX
- Pi標準操作の実装可能範囲の調査、サードパーティExtensionとの互換性対策
- テスト方針、CI、開発順序、Issue / PRへの分割、技術的な小さな設計判断

**不必要に大規模な独自基盤を構築せず、既存のPi機能と小さな構成要素を優先してください。** 決定事項に反する変更や、製品体験に影響する代替設計が必要な場合は、理由・トレードオフ・推奨案を提示して判断を仰いでください。

## 5. 実装前に確かめたいこと

最初に**小さなPoCで成立性を判断**してください。検証手順・技術選定・判定方法は実装担当で考えます。少なくとも次を確かめます。

- abduco管理下で通常Pi TUIを非Attach起動し、後からPCでAttach / Detachできるか。
- PCがAttachしていない間も、Remote Control Extension経由でPiを操作し、状態を取得できるか。
- 複数Piの同時実行と、PCで通常起動したPiへの接続が共存できるか。
- Hostの停止・再起動やOSのサービス管理下で、Piプロセスの生存・再発見・復帰をどこまで保証できるか。
- macOS / Linuxでabducoを安全かつ再現可能に同梱できるか。
- Pi標準操作と第三者ExtensionのUI対応に、どのような制限があるか。

PoCで不成立の項目が出たら、**abduco以外への無断切替やPi RPC方式への変更をせず**、結果と代替案を提示してください。成立した範囲から、動く縦断的なMVPを作り、段階的に機能を充実させます。

## 6. 完成に向けた判断基準

- PCで普通に使うPiを、同じプロセスのままスマホから操作できる。
- スマホから複数の独立したPiを起動でき、PCから同じTUIへ接続できる。
- スマホの切断・再接続や会話セッションの切替に安全に追従する。
- ユーザーが既に導入しているPiの設定・Skills・Extensionを活用できる。
- ネイティブなスマホUXと、可能な限り簡単な導入体験を実現する。
- 実装できない標準機能やExtension互換性の制約を隠さず明示する。
